These tests show that Proofable stops agent actions nobody allowed before they run, and keeps a signed record of every decision that anyone can check.

[Check your own agent tools](https://proofable.me/prove), the MCP servers your agents connect to.

## Results

### Every unauthorized action stopped before it ran

8 of 8 live tests passed on the production service. The six actions the agent wasn't allowed to take never ran, and the two allowed actions did.

### Forged records caught

The signature check caught 150 of 150. A check that only looks for the right format caught 0 of 150, because every forged copy was still well-formed.

### Reusing a result instead of redoing it

Reusing a finished result took 3.7 ms against 2.79 s to redo the job, about 750 times faster, at zero AI cost. Redoing it used 2,426 AI tokens and reusing it used none.

## Check it yourself

### Verify the records offline

Check all 15 signed records from the eight tests offline, with no account:

```sh
git clone https://github.com/proofable/docs
cd docs/public/evidence/aaif/authority-at-dispatch/2026-10-08-eight-case
sha256sum -c SHA256SUMS
npm install @proofable/sdk@0.1.6
node verify-portable-proofs.mjs
```

### Forge a record

This check takes the same 15 signed records, forges each one ten ways, and verifies every copy offline. Every genuine record must pass and every forged copy must fail.

```sh
cd docs/public/evidence/checks
npm install
node tamper-check.mjs
```

| Forgery | Copies | Caught |
|---|---:|---:|
| Edit the content | 15 | 15 |
| Swap the owner | 15 | 15 |
| Impersonate the signer | 15 | 15 |
| Backdate the timestamp | 15 | 15 |
| Change the chain | 15 | 15 |
| Upgrade the check type | 15 | 15 |
| Redirect the reference | 15 | 15 |
| Flip one signature bit | 15 | 15 |
| Replay another record's id | 15 | 15 |
| Transplant another signature | 15 | 15 |
| **Total** | **150** | **150** |

Every forged copy is still well-formed, so a check that only reads the format accepts all 150. The signature check rejects all 150 and accepts all 15 genuine records.

### Reuse a result

[This record](https://proofable.me/proof/0xcf67dcc3cc9c203136daf9905a422601652fd76cce437e2cbf56967e3a8117e6) is a finished agent job from the public kit. Producing it took 2.79 s and 2,426 AI tokens. Anyone can read it by its id and verify its signature, with no account:

```sh
cd docs/public/evidence/checks
node reuse-check.mjs
```

Measured on October 20, 2026, it verified offline in 3.7 ms (median of 10 runs) with zero AI tokens. That is about 750 times faster than producing the result again.

### How the AgentGovBench run works

[AgentGovBench](https://github.com/agentic-control-plane/agentgovbench) is an open library of 48 agent-governance scenarios in eight areas: audit completeness, cross-tenant isolation, delegation provenance, fail-mode discipline, identity propagation, per-user policy, rate limits and scope inheritance. Each scenario is tagged with the NIST AI RMF controls it tests.

We ran the library at commit `e0ce93a` against the exact policy code the live service runs, matched to it by hash, next to two comparison setups. The run called that code directly, so it measures the decision logic rather than the hosted service end to end. Last run: October 17, 2026.

| Setup | Scenarios passed |
|---|---|
| Proofable policy engine | 48 of 48 |
| A gate that allows everything | 28 of 48 |
| No governance | 13 of 48 |

### Rerun the live tests on your own account

The kit drives the same eight tests against the live service on an account you control and writes signed records you can compare with the ones above:

```sh
git clone https://github.com/proofable/docs
cd docs/public/evidence/aaif/authority-at-dispatch/reproduce
npm install
export PROOFABLE_ACCESS_KEY=npk_...
export AAD_OPERATOR="Your Organization"
node aad.mjs setup
node aad.mjs run
node aad.mjs verify runs/<run-id>
```

The tests run agent jobs on a Pro account. Create the access key under
[Profile, Account tab, Access keys](https://proofable.me/profile?tab=account).

The same records are part of the [AAIF Identity & Trust working-group comparison](https://github.com/aaif/wg-identity-and-trust/issues/13) at the Linux Foundation.
